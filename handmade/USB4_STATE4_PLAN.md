## SEQUENCE EFFECT (the HW-checkable contract)
b0b4 is the TUNNEL-POWER-ON + 20G rate-change + RxPLL-reset + per-lane OS1-arm engine that PRECEDES (and primes) the state-5 CL0 walker. It does NOT itself drive SB[0xA0]/[0xA1] to 0x02; it drives them to the 0x01 staging and arms the Trig that state-5 fires. The exact HW-checkable transitions a correct transcription MUST produce, in order, on the live AMD-x2/USB4 path (0x0776==0 normal connect, both lanes present): (1) E716 = (CA06&0x1F)|0x60 with CA81.0 cleared [if 0x0AF1.0]; (2) e305: CA06 61->01 (or |0x20) keyed on lane-mode, B402.1 cleared (PERST release), B403 link-speed + B431 width programmed; (3) e26a/cdc6: E764 0x14->0x19 (the train-arm), C656.5 set (PwrOn), UART '[PcieTunnel-PwrOn]'; (4) SB[0x15]/SB[0x0C] OS descriptors written per lane (0x82/0xa2 + (old&0x80)|3), each followed by the d5da SB[0x10]/SB[0x2C].2/CC10(0,0x0B,1) handshake; 0x081e.7/0x081f.7 OS-armed latches set; (5) CC37.2 set->cleared bracketing d3b0(Chg2 20G: SB[0x65] bit4/bit5, UART 'Chg2 20G')/e980(C2C9/C349 rate desc, C2A8/C328 bit7 START, C2D0.5+C350.5 rate-lock)/e9e7(UART '[RstRxpll...]', C20E 0xFF->0x00, CC10(1,0,0x14)+CC10(2,0,0x28), UART '[Done]'); (6) b8db: UART '[CDRV ok]'; (7) CA60.3 set; (8) L0/L1 OS1 trigger: SB[0xd8]=0x02 (L0, the OS1 ordered-set that moves SB[0xA0]) / SB[0x5a] (L1), UART '[L0 OS1]'/'[L1 OS1]', 0x075b/0x0759=0x10 (L0) / 0x075c/0x075a=0x10 (L1) — these are the e672 state-5 ENTRY conditions; (9) ec51: CCE0.2 set, CCE1=0x01, CCE2=CCE3=0xFF (arm the [Trig] state-5 fires); (10) 0x074e:0x074f = CCE4:CCE5 (latch negotiated width); (11) eb62(0,5): 0x06ED=5, UART '[SB P05]'. NET observable success of b0b4 alone: UART shows [PcieTunnel-PwrOn] -> Chg2 20G -> [RstRxpll...][Done] -> [CDRV ok] -> [L0 OS1][L1 OS1] -> [SB P05], with E764 14->19, CA06 61->01, SB[0xd8]=0x02 armed, and 0x075b/0759/075c/075a=0x10 set so e672 enters state-5 (NOT eb62(0,0)). SB[0xA0]/[0xA1] reaching 0x01->0x02=CL0 is STATE-5's job, but it is UNREACHABLE unless b0b4 leaves those four 0x075x bytes nonzero and the Trig armed — so the checkable contract for THIS round is: the six UART markers in order + the four 0x075x=0x10 latches + E764=0x19 + CA06=0x01.

Use CODE_BANK1:: prefix for disasm; the raw disassemble tool TRUNCATES e07d AND d5da at the first RET-less basic block (shows only 3/4 instrs) — the file bytes (file_off=addr-0x8000+0xFF6F) are ground truth, NOT the 3-instr disasm. Ghidra bank1 DECOMPILE is garbage (invents string ptrs, fake recursion on 538d, void stubs on 051b, bogus 'return cVar3' in L1 branch). Use raw asm.
- phy_cc10_cmd_wait ARG ORDER is (subcmd,cc12,cc13) — CONFIRMED in boot_phy.h:38. Stock e80a takes (R4=cc12,R5=cc13,R7=subcmd). So b226's R7=2,R4=0,R5=0xc8 => phy_cc10_cmd_wait(2,0,0xc8) [b226=settle], d5da's CC10 => phy_cc10_cmd_wait(0,0x0B,1), d3b0 commit => phy_cc10_cmd_wait(0,0xc8,2)... WAIT: d3b0 sets R4=0,R5=0xc8,R7=2 => phy_cc10_cmd_wait(2,0,0xc8). RE-DERIVE every call from R7/R4/R5 at each site — do NOT copy the decompiler's arg order. This is the #1 transcription-error risk.
- XDATA 0x0AA1/0x0AA2 COLLISION: pd_dispatch.h already uses 0x0AA1=PD MessageType, 0x0AA2=PD MessageID. e26a uses the SAME addresses as PwrOn/Deassert flags. These are the same physical bytes — verify there is no live-time clobber between PD dispatch and b0b4 (different FSM phases, likely safe, but confirm before relying on 0x0AA1==1 selecting the PwrOn branch).
- do-NOT-reuse usb4_connect_u4 (sb.h a48c-a516): MEMORY documents that the FULL connect_u4 tail REGRESSED E302 to mode0 (e7ae C006/C00E PHY-lock wait disturbs training). It touches the SAME CA06/E716/CC37/B402 registers but is a DIFFERENT routine. b0b4 must be transcribed from ITS OWN asm, not by reusing connect_u4 fragments.
- BUSY-POLL BOUNDING: d5da SB[0x2C].2 spin, e980 C2D0.5/C350.5 rate-lock spins, cdc6 E762.4 gate — ALL must get bounded guard counters (project rule: no unbounded stock busy-polls). An unbounded spin that never completes on HW hangs the super-loop.
- PLANE DISCIPLINE: SB[off]=DPX=1 0x2800+off (SB_RD/WR); SB2 lane block=DPX=1 0x2900+off (NEW accessor needed); P1[0x0100]=DPX=1 0x0100; but C2xx/C3xx/CA06/CC37/E716/E764/B40x/C656 = bank0 PLAIN XDATA (DPX=0/PR()). Routing a C2xx through SB/P1 accessors corrupts the access. e980's regs are all DPX=0.
- UNDER-MAPPED DEEP NODES: e305's ee29 (df61/e74e SERDES descriptor) + a840 (B403/B431/ced1/e2c9 speed-table) and b8db (CDRV compare body) are NOT fully mapped in the probe — only entry/register touches. Transcribing them now would FABRICATE the sequence (the project's documented failure mode). They need their own disasm round FIRST.
- STRING-vs-REGISTER mis-ID corrected: 0x1fc0/0x1fcb (Chg2 10G/20G), 0x1fd6/0x1fe6 (RstRxpll/Done) are CODE strings printed by 538d=uart_puts, NOT PHY registers. The MEMORY note 'd435/e9e7 write to 0x1fcx/0x1fd6 regs' is WRONG — do not emit register writes there.
- r7/d5da PARAM INHERITANCE: 96fe leaves R7=1 (its tail MOV R7,#1) so the d5da after an OS-arm runs param==1; but after e07d (retrain) d5da runs param==0, and the decompiler hides this. The d5da param selects which of 3 branches runs — must pass the correct literal at each call site.
